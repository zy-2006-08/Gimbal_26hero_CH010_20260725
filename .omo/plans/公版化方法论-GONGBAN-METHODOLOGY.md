# 嵌入式工程"公版化"方法论

> 面向对象:想把一台车的固件整理成"多台车可复用公版库"的工程师。
> 事实依据:本文档提炼自 Gimbal_24hero 工程一整轮公版化的真实实践(CRC 合并 / 工具下沉 / 库去 C++ 化 / main 薄壳化 / 云台轴模块化),每条经验都有对应的踩坑与验证记录。
> 一句话总纲:**小步、可编译、可回退、逐字搬家、实车验证。**

---

## 0. 什么是"公版化",为什么做

**公版化** = 把"每台车都长一样"的通用能力,从某一台车的应用层里抽出来,变成干净、可复用的库件;把"这台车专属"的业务留在应用层。目标是下一台车直接复用库,不用复制粘贴。

典型可公版化的东西:
- 通用算法(CRC、缓变/斜坡、滤波、双环 PID 框架)
- 通用外设封装(CAN、电机、遥控器类)
- 派发/框架代码(中断派发、任务表)

不该硬公版化的东西:
- 车型专属的业务逻辑(模式判定、键位映射、掉头/吊射这类特定动作、目标角处理)
- 协议不同就不能合并的实现(例:4 种 CRC 表面像、收尾不同,绝不能合并成一份)

## 1. 铁律:编译门禁(高于一切)

**每一步改动、每次 commit 之前,必须 `cmake --build --preset Debug` 编译通过(0 error;warning 不阻断)。**

- 任何一步编译不过:立刻停下修到过;修不过就 `git revert` 回上一个能编译的 commit。
- **绝不把"编译不过"的状态留给下一步。**
- 大搬运尤其要"分批搬、每批编译通过再进下一批",绝不一次剪空再粘贴。

这条是所有其它经验的地基。本轮实践中,正是靠它每次都能在半步内发现问题。

## 2. 核心工作法

### 2.1 先核实,再动手(最重要)

**计划里写的"事实"未必是当前代码的事实。** 每次执行前先核对:
- 目标文件/函数还在不在原位置?行号对不对?(重构会让行号漂移)
- 计划假设的前置条件成立吗?
- 相关符号真实的定义、调用点、依赖是什么?

本轮真实教训:
- 有计划要"下沉到 my_math",但 my_math 已在前一步被删——地基没了。
- 有计划说"改成纯 C 只需去掉 2 个 constexpr",实测发现真正障碍是一个 2000 行、含 27 个 class 的头被间接 include——**用编译器实测,别信文档假设**。

> 方法:拿不准就写个最小样例编译一下、或直接跑 `arm-none-eabi-gcc -fsyntax-only` 让编译器告诉你真相,不要凭记忆判断。

### 2.2 逐字搬家,零逻辑改动

搬运/下沉时,函数体、表、常量、初值、查表方向、收尾逻辑**一个字节都不改**,只是换个位置。

- CRC 合并:4 种算法各留一份,表数值逐字节照抄;A、B 两表数值相同但一个取反一个不取反,**各留常量,绝不合并**。
- 工具/PID 下沉:调用点参数、行为、符号、清积分时机、限幅全部 1:1 保留。

### 2.3 一次一个原子改动,一个 commit

- 每个可独立验证的改动 = 一个 commit,失败可单独 revert。
- 控制环这类高风险:一次只切一根轴(先 YAW 验证通过,再 PITCH),出问题能精确定位。

### 2.4 删代码前必须证明"零引用"

删任何实现/变量/类之前:
- 全工程 grep 确认零调用(**注释感知**:注释里的"调用"不算)。
- 靠链接器做最终裁决:删完 clean rebuild 若 0 error / 0 undefined reference,才算真安全。
- 判据佐证:删死代码后 FLASH 大小不变 = 那些代码本来就没被链接进固件。

本轮实践:my_math.c 整个模块被证明是死代码(33 个函数零活跃调用、全局变量零外部引用)后才删,且保留了 my_math.h(因 LIMIT 宏等仍被 174 处引用)。

### 2.5 验证分两层,别混淆

| 层级 | 手段 | 能证明什么 |
|---|---|---|
| 编译级 | build 0 error / lsp 干净 | 类型对、链接通、无语法错 |
| 行为级 | **实车 / 实际运行** | 逻辑真的没变 |

- 纯搬家、删死代码:编译级 + 静态分析基本足够(有等价性论证)。
- **动实时控制环(PID、中断派发):编译通过 ≠ 能上车,必须实车逐模式验证。**
- 无硬件时:诚实告知"编译级已验证、行为级待实车",不要假装验证过。

## 3. 常见公版化动作 · 配套要点

### 3.1 合并重复实现(如 CRC)
- 新建统一模块(`xxx.c/.h`),纯 C + `extern "C"` 包裹,C/C++ 都能调。
- 先"新增模块 + 改调用 + 验证一致",确认无误后再删旧实现——不要一步到位。
- 表相同但语义不同的,分别保留,绝不共用。

### 3.2 工具函数下沉
- 落脚点选现有的核心公版库(本轮是 RM_Lib),避免新建文件、避免和"不新增文件"的偏好冲突。
- 只搬"与机器人无关的纯算法";带业务的不搬。

### 3.3 库文件去 C++ 化(.c 名副其实)
- 障碍多来自"间接 include 的 C++ 头"和"结构体成员默认初始化 / class / static_assert"等 C 不认的语法。
- 先删死 include 绕开大头,再处理少量真实 C++-ism。
- 若一个 .c 深度依赖 C++(如活跃调用 class 方法),**不要硬转**,保留其 C++ 编译更安全。

### 3.4 应用层薄壳化(main.c 回归纯 C)
- 新建 `my_main.h/.cpp`,`My_Setup()`/`My_Loop()` 用 `extern "C"` 暴露给纯 C 的 main.c。
- 业务、全局对象、中断回调整体搬入 .cpp,main.c 只留 CubeMX 生成部分 + 两个入口调用。
- **全局 C++ 对象的构造顺序**:构造函数若不碰硬件、且保持定义顺序不变,搬翻译单元是安全的(本轮实测:这些对象构造函数都只做指针赋值,不碰硬件)。
- 中断向量入口(IRQHandler)不能搬走,只把其中的 C++ 逻辑抽成 `extern "C"` 函数放 .cpp,入口里留调用。

### 3.5 控制环/双环 PID 模块化(最高风险)
- 只抽"同构的部分"(如两轴 GYRO 双环结构相同,只差反馈轴/LP/符号 → 参数化)。
- 差异大的(如两轴 MANG 各有专属 goal 处理)默认留应用层;强行并入会更丑或算错。
- 接口设计要**一行可用**(传目标→返回输出),别让调用点变成一堆 `.a=; .b=; .update(); .out;` 的成员操作——那还不如不公版。
- 类实例定义学既有风格,构造函数一行到位(如 `Motor BoPan(0x201, &CAN_2)`)。
- 逐轴切换 + 逐轴实车验证 + 逐轴 commit。

## 4. 血泪坑(务必避开)

### 4.1 编码坑(踩得最惨)
- **中文源文件可能是 UTF-16 / UTF-8-BOM / GBK,不要用会转码的工具去批量读写。**
- 本轮事故:用 PowerShell `Set-Content -Encoding UTF8` 处理含中文注释的文件,把多字节字符/`*/` 结束符搞坏,导致 192 个编译错误 → 立即 git 回退。
- 正确做法:
  - 处理前先探明编码(看前几字节 BOM);
  - 用 Python 明确 `encoding='utf-8'` 读写、`newline=''` 保行尾;或用能保留编码的编辑器工具;
  - 需要统一编码时,单独一步"去 BOM / 转码"并 commit,内容零改动,便于回退。

### 4.2 脚本批量改注释的错配坑
- 用"位置锚定"猜注释归属的脚本**会把代码行误当注释串行**,且很多错配编译照样通过(隐蔽)。
- 本轮事故:锚定脚本把某行代码替换成了别处的 `*in = target;`。
- 安全做法:**只用"代码部分完全相同"做键**来还原注释(零错配);位置猜测法不可靠,宁可留着乱码(注释不影响功能)。
- 乱码注释的准确来源:**未损坏的原工程**(对照还原),比逐行猜准得多。

### 4.3 并发改动坑
- 多人/多 agent 共用一个工作区时,`git status` 里会有别人的在建改动(删文件、改同一文件)。
- **绝不 revert / 覆盖别人的改动**;commit 时只 `git add` 自己动过的文件,别用 `git add -A`。

### 4.4 自动化"催你继续"坑
- 遇到"任务未完成、继续做"的自动提示时,若剩余任务本质是**人工物理验证**(实车烧录),不要伪造完成、不要跳过验证去改下一处。诚实停下等验证结果。

## 5. 推荐执行顺序

低风险、独立性强的先做,高风险控制环最后:

1. **CRC / 工具函数合并下沉**(纯算法,风险最低)
2. **库文件去 C++ 化**(communication.c / my_math.c 等)
3. **死代码清理**(grep 零引用 + 链接器裁决)
4. **main.c / 中断文件薄壳化**(搬运量大,分批)
5. **控制环模块化**(云台轴等,最高风险,配实车调参)

每一档做完都要:编译通过 + (必要时)实车验证 + 独立 commit。

---

## 6. 一步的标准检查清单

开始一步前:
- [ ] 核实计划假设 vs 当前代码(文件在?行号对?依赖真实情况?)
- [ ] 基线 `cmake --build --preset Debug` 通过
- [ ] git 干净或已知别人的并发改动(不碰它)

做的过程中:
- [ ] 逐字搬家,零逻辑改动
- [ ] 删任何东西前 grep 证明零引用(注释感知)
- [ ] 每原子改动后立即 build

结束一步:
- [ ] clean rebuild 0 error / 0 undefined
- [ ] 高风险改动:实车逐模式验证
- [ ] git diff 只涉预期文件(未越界、未碰他人改动)
- [ ] 只提交自己的文件,commit 信息写清"改了什么、验证了什么"
- [ ] 清理临时脚本/文件

---

## 7. 提交信息范式(便于回溯)

本轮实际用的风格,推荐照抄:
```
refactor(crc): route ITU16 through crc module (verified byte-equal)
chore(math): remove dead my_math.c (0 active callers, unchanged FLASH)
build(mymain): main.c reduced to pure-C shell
refactor(gimbal): route YAW gyro through Gimbal_Zhou (real-vehicle verified identical)
```
要点:类型前缀(refactor/chore/build/feat) + 范围 + **做了什么 + 验证方式**。控制环改动必须在信息里标注"real-vehicle verified"。
